# Pewpew Development Guidelines

This file consolidates development requirements, best practices, and key notes.

## Core goals
- Preserve vanilla behavior by default; any behavior changes must be opt-in and documented.
- Improve main-thread performance with safe, deterministic multithreading.
- Keep plugin compatibility intact (Bukkit/Paper APIs remain main-thread by default).
- Keep implementation simple and clean; avoid redundant logic.

## Threading model
- Single-writer per world: each world is mutated by its own tick thread during the parallel phase.
- Main thread acts as scheduler: dispatches world ticks, waits at a barrier, then runs commit/post-tick work.
- World tick threads are long-lived `TickThread` instances; no per-tick thread creation.
- Tick is barriered: the main thread waits for all world tasks; tick time may exceed 50ms instead of falling back.
- Off-thread compute (not a world tick thread) is read-only and uses snapshots; side effects are queued for main-thread commit.
- No Folia-style regionized ticking; per-world ticks + targeted async is the baseline.

## Thread-safety constraints (Paper 1.21.8)
- Only world tick threads may mutate world state; other threads are read-only.
- Do not access live chunks off-thread; use snapshots for reads.
- Avoid shared mutable AI caches off-thread (NodeEvaluator/PathFinder state).
- Do not use shared static TargetingConditions off-thread (updated per tick).
- Avoid live PalettedContainer reads off-thread (reads are unsynchronized).

## Compatibility constraints
- All plugin callbacks run on the main thread; use commit queues to preserve vanilla ordering.
- World load/unload happens only at a barrier point (no world ticks in flight).
- Each world has a stable owner thread or a safe handoff protocol.
- Datapack functions and triggers run on the main thread before world ticks, preserving vanilla order.
- Plugin and datapack logic that spawns or mutates entities must run on the main thread (or the owning world tick thread during the parallel phase) with explicit world context.

## Snapshot requirements
- Snapshots are built once per tick on the main thread or owning world tick thread.
- Store section versions, entity versions, and POI versions for validation.
- Snapshots use immutable data (copied or packed), never live references.

## Pathfinding rules
- Async pathfinding must use snapshot-backed PathNavigationRegion.
- Pathfinding caches are per-task (no shared NodeEvaluator state).
- mob.onPathfindingStart/Done must run on main thread.
- If validation fails, discard and retry next tick (no same-tick fallback).

## Sensor precompute rules
- Off-thread work limited to candidate lists (entity ids + distances).
- Main thread applies TargetingConditions and sets memories.
- Sensors that fire Bukkit events (e.g., TemptingSensor) remain main-thread.

## Test automation requirements
- Correctness tests run automatically on every build; no human intervention required.
- Perf A/B tests run via an explicit task (e.g., `./gradlew :pewpew-server:pewpewPerfAB`).
- Provide a single Gradle task to run all correctness tests (e.g., `./gradlew check`).
- Integration tests run headless with timeouts and cleanup.
- Perf checks use fixed seeds and scenarios; fail on regression thresholds.
- Perf checks are A/B: compare vanilla Paper vs Pewpew on the same machine and config.
- Every code change includes a correctness unit test and an automated performance report.
- Perf reports are generated by tests and summarized under `docs/pewpew/findings/perf-report.md`.

## Rebrand requirements
- Default brand name is Pewpew; avoid changing package names.
- Branding flows from ServerBuildInfo to CraftServer and brand payloads.
- Update build metadata and manifest attributes for Brand-Id/Brand-Name.

## Patch workflow (strict)
- Do not edit `pewpew-server/paper-patches` directly.
- Do not edit `pewpew-server/minecraft-patches` directly.
- Work in `tmp/` with a fresh, patched Paper source:
  - Clone upstream Paper at the target version and run `./gradlew applyPatches` there.
  - Apply Pewpew changes on top of the patched sources, then commit locally.
  - Generate patches via `git format-patch` (or equivalent) from the tmp repo.
  - Copy the resulting patch files into `pewpew-server/paper-patches` or `pewpew-server/minecraft-patches` as appropriate.
- When building, apply Pewpew patches after all Paper patches (`./gradlew :pewpew-server:applyAllServerPatches`).
- Rebuild the full patch series only when intentionally refreshing everything (`./gradlew rebuildAllServerPatches`).
- Keep patches minimal and derived only from the patched working trees.

## Implementation best practices
- Keep changes small, layered, and easy to bisect.
- Prefer deterministic ordering and stable outcomes.
- Use feature flags for new async systems.
- Add minimal instrumentation to validate wins and catch regressions.
